Make a game for Game Scroll

Every game in the feed is one small JavaScript file. Write yours, send it in, and once it's merged it streams to every player's phone within minutes, credited to you. No app update, no store review.

How it works

  1. Write one file. Your game lives in src/games/your-game.js. It draws on a canvas and reacts to touches, and the engine (gs) gives it physics, sound, effects, 3D, opponents that learn and much more. The app handles the rest: the start screen, the game-over screen, scores, credits, sizing for every phone. You can write it yourself or with an AI tool.
  2. Try it on your phone. Run the app on your computer and open it on your phone over Wi-Fi.
  3. Check it with one command. npm run check your-game plays it, folds the screen, compares it with every game in the feed and measures its speed against real phones, and says what to fix, line by line.
  4. Open a pull request on GitHub. The same checks run again, then Rob plays it.
  5. It goes live. When it's merged, your game streams into the feed for everyone, with your name on it.

You'll need some JavaScript. If you've made something with an HTML canvas before, you're ready. If not, copy the starter game below and change one thing at a time.

The rules

  • Original games only. Take inspiration from a genre or a mechanic (falling blocks, kart racing, platformers), but don't recreate a specific existing game: no copied names, characters, art, music, levels or look, even renamed.
  • A new mechanic. The goal is 1,000 games that each play differently. A reskin or harder version of a game already in the feed won't be merged. Play the feed and check the ideas list first.
  • Quick to learn, quick to play. A player should get it from a one-sentence hint. A round lasts about 20 seconds to 3 minutes.
  • Self-contained. One file, everything drawn in code. No image, font or sound files, no network requests, no tracking, no ads, no links out of the app.
  • Touch first. Every game must be fully playable with touch alone. Sensors are welcome as an extra.
  • Family friendly. Cartoon action is fine. No gore, hate, real-money gambling, or anything you wouldn't show a 12-year-old.

1. Get set up

Option A: on your computer

Install Node.js 26 (the current LTS) and Git. Then fork the repository on GitHub (you need a free GitHub account) and run:

git clone https://github.com/YOUR-NAME/game-scroll.git
cd game-scroll
npm install
npm run dev

Open the address it prints. On a desktop browser, Space starts a game, the arrow keys steer and ↓ goes to the next game. To try it on your phone, open the "Network" address on your phone while it's on the same Wi-Fi.

Option B: in your browser, nothing to install

Fork the repository, then on your fork click Code → Codespaces → Create codespace. You get an editor in the browser. In its terminal, run npm install and npm run dev, then open the forwarded port it offers. GitHub gives every account free Codespaces hours each month.

2. Write your game

Quickest start: npm run new my-game --style pocket writes a small game that already plays, in any style (phone, pocket, color, advance, console, nextgen, ar or board). It starts the way a finished game does: a fixed tick, a "Tap to start" gate, one-call effects, a soundtrack, a save slot and its feel numbers in one block of knobs. Then make it your own.

Or start from scratch: create src/games/tap-bubbles.js (the file name must match the game's id). This is a complete, working game you can start from:

import gs from '../gamescroll.js';
const { Feel } = gs.effects;
const { Ready } = gs.rounds;

const W = 360, H = 640;

function make(api) {
  const feel = new Feel(), ready = new Ready();
  const K = gs.tweak('Feel', {                // knobs: the numbers that set how it feels
    rise: [90, 40, 200, 'how fast bubbles float up'],
    faster: [4, 0, 10, 'extra speed each second'],
    size: [24, 14, 40, 'bubble radius'],
  });
  let bubbles, score, t, missed;
  return {
    reset() { bubbles = []; score = 0; t = 0; missed = 0; feel.clear(); ready.reset(); },   // ALL round state here
    update(dt) {                              // dt is in seconds
      feel.update(dt);
      if (!ready.update(dt)) return;          // nothing moves until the first tap
      t += dt;
      if (Math.random() < dt * (1 + t / 10)) bubbles.push({ x: 30 + Math.random() * (W - 60), y: H + 30 });
      for (const b of bubbles) b.y -= dt * (K.rise + t * K.faster);
      const gone = bubbles.filter(b => b.y < -30).length;
      if (gone) { missed += gone; bubbles = bubbles.filter(b => b.y >= -30); feel.hurt(); }
      if (missed >= 3) { feel.lose(); api.over(); }
    },
    draw(c) {                                 // a 2D canvas context, W x H units
      c.fillStyle = '#16212e'; c.fillRect(0, 0, W, H);
      feel.begin(c);                          // everything up to feel.end() shakes
      c.fillStyle = '#5aa8ff';
      for (const b of bubbles) { c.beginPath(); c.arc(b.x, b.y, K.size, 0, 7); c.fill(); }
      feel.end(c, W, H);                      // particles, pop-ups, flash
      ready.draw(c, W, H);                    // "Tap to start" until the first tap
    },
    down(x, y) {                              // already in game units
      if (ready.go()) return;                 // the first tap only starts the round
      const i = bubbles.findIndex(b => Math.hypot(b.x - x, b.y - y) < K.size + 8);
      if (i < 0) return;
      const [b] = bubbles.splice(i, 1);
      api.score(++score);
      feel.coin(b.x, b.y, { text: '+1' });    // particles, a sound and a buzz in one call
    },
  };
}

export default {
  id: 'tap-bubbles', title: 'Tap Bubbles',
  tag: 'Casual · Reflex',                     // "<Style> · <Genre>"
  retro: false, w: W, h: H,
  tick: 60,                                   // the same game on every phone
  music: 'happy',                             // a soundtrack in one line
  goal: 25,                                   // the score that counts as a win
  hint: 'Pop the bubbles before they float away. Miss three and it is over.',
  make,
};

Then jump straight to it: open the browser console and run __gs.only('tap-bubbles'). Press ` (backquote) for the debug overlay: frame rate, slow motion, frame stepping and hitboxes. Save your file and the game reloads in place.

Knobs. The numbers that set how a game feels live in one gs.tweak('Feel', { ... }) block. In npm run dev they show as sliders while you play, and Save to file writes them back. npm run knobs tap-bubbles lists or changes them, and the feel words list says which knob a word like floatier, snappier or fairer moves. npm run watch tap-bubbles rise*0.8 plays it before and after a change from the same start and saves a strip of frames, so you can see the difference.

What your game gets and gives

Your game objectWhen it's called
reset()Before every round. Put all round state here so "Play again" starts clean.
update(dt)Every frame while playing. dt is seconds since the last frame.
draw(ctx)Every frame. Draw the whole frame; nothing is cleared for you.
down / move / up(x, y, id)Touches, in game units. id tells fingers apart for two-thumb controls.
key(k, isDown)Optional keyboard support for desktop.
resize(w, h)Optional, for games that grow to fill big screens.

Your game calls api.score(n), api.over() and api.win(). To remember things between plays, like unlocked levels, use its own save slot: api.save(data) and api.load(fallback). Saves follow the player to a new phone. A bigger world the player builds can stay on the phone with api.saveLocal(data). The app draws the score at the top centre: keep your own HUD out of api.scoreArea().

The apiWhat it does
api.score(n)Sets the score. Reaching goal wins credits; the game keeps going.
api.over()Ends the round.
api.win()Wins right now, for games with a natural end.
api.has('item')True when the player bought that shop item for this run.
api.location()Where the player is, rounded. Needs location: 'coarse' in your game. Location games.
api.watchLocation(cb)Calls cb each time the player moves to a new spot, until the round ends.

The hint and the genre in tag also feed the recommender, so mention the control (tap, drag, tilt...) and the genre honestly.

Making it with an AI tool

Many makers use an AI helper: Claude, ChatGPT, Gemini, Copilot, Cursor and the rest. The repository is set up for them.

  • Coding tools that work in the repository read its instructions by themselves (AGENTS.md, and CLAUDE.md or GEMINI.md for those two). Open the repository in the tool and ask, for example, "Make a new Pocket game where you herd sheep with a dog by tilting the phone." Claude Code also has a /make-game skill.
  • The Game Scroll MCP server (scripts/mcp.mjs) lets the tool ask the engine instead of guessing: a short guide to any part of gs, how real games use it, which knob a feel word moves, a new game from a template, every check in one report, the speed report, and play and watch, which plays the game and sends back pictures and numbers, before and after a change. Claude Code finds it by itself (.mcp.json); Cursor, Codex, Gemini CLI and VS Code take one line of setup.
  • Chat apps: npm run ai-prompt pocket > prompt.txt (or any style) writes one prompt with the rules, the kit and a starter game. Paste it in with your idea, save the code it gives you as src/games/<id>.js, run npm run check <id> and paste the report back to have it fix what failed.

So "make the jump floatier" becomes one number the tool can find, change and show you. You're still responsible for what you send in: play it, read it, and check the names and characters are your own. More in making games with AI tools.

3D games on phones

  • 60 frames a second, or 30 and 30 made. On a phone, a 3D game aims for a steady 60. Where it can't hold 60, the app draws 30 and frame generation (GSFG) makes the 30 in between, and goes back to 60 when there is room. Low phones, and any phone that is warm or saving power, play at 30 with 30 made. You don't set any of this: keep your game's work light and the app picks.
  • Made after Play. In the feed, a Next Gen, AR or Board card is only a picture (the game as it looked at the end of its last round on that phone, or a cover), so scrolling past it costs nothing. Play shows a loading screen while the app makes your game, runs reset(), draws the first frames and builds every shader they need, so the round never stutters in its first seconds. Make what a round needs in make(), reset() or its first update(), not a few frames in.
  • Smoothness is part of the game. The speed report (in npm run check, or npm run speed <id> alone) times your frames on a slowed processor, names your slowest lines and the garbage they make, and for 3D games counts draw calls, triangles and shaders built mid-play against low, mid and top phones. Over the budget fails the check.

The web version of Game Scroll (in a browser, for trying games) leaves Next Gen and AR games out of its feed and plays Board games in 3D without AR, so those styles need the app. The other styles play the same everywhere.

Big screens and foldables

Players use everything from small phones to unfolded Galaxy Z Fold and iPhone foldables, and can fold mid-game. By default your canvas is scaled to fit. To fill the extra space, add maxW and maxH and a resize(w, h) method; the app picks the best size and tells you. Keep the game fair at every size.

AR games: 3D in the player's real room

AR · 3D is the newest style. The back camera fills the screen and the phone's motion sensor turns the 3D camera, so a saucer, a bin or a hoop stays put in the room while the player moves their phone around. Shadows fall on the real floor. It's "look-around" AR: players turn, tilt and look up and down on the spot, but walking isn't tracked.

The games in the feed now show what works: Saucer Swarm (turn to aim, tap to zap saucers swooping round the room), Bin Flick (flick paper balls into a bin on your floor) and Hoop Drone (fly a tiny drone through glowing hoops wherever you point).

The AR kit

AR games use gs.ar, built on the Next Gen HD renderer, so you get real materials, reflections and shadows. A minimal AR game looks like this:

import gs from '../gamescroll.js';
const { want } = gs.device;
const { ARView, arNote, FLOOR } = gs.ar;
const { pbr, rbox, THREE } = gs.hd;

function make(api) {
  want('motion');                      // iPhones ask for motion access on the Play tap
  let v;
  return {
    reset() { v?.off(); v?.recenter(); /* set up the round */ },
    update(dt) { if (!v) return; v.live(); /* game logic; v.off() before api.over() */ },
    draw(c) {
      if (!v) { v = new ARView(); /* build meshes, add them to v.scene */ this.reset(); }
      v.look();                        // motion sensor (or drag) turns the camera
      v.draw(c, W, H);                 // camera picture + your 3D scene
      v.pointers(c, W, H, [{ p: target, col: '#8affdc' }]);   // arrows to things off screen
      arNote(c, v, W, H);              // says when a fallback is on
    },
  };
}

export default {
  id: 'my-ar-game', title: 'My AR Game', tag: 'AR · Shooter',
  retro: true, era: 'ar', pal: 'grape',
  w: 300, h: 460, maxW: 600, maxH: 680,
  goal: 20, hint: 'Turn your phone to aim... No camera? Drag to look around.', make,
};

Making it feel real

  • Use real sizes and distances. The phone is the eye, about 1.3 m above the floor (FLOOR is -1.3) and straight ahead is -z. Put things 1.5 to 7 m away at their real size: a bin is about 38 cm tall, a saucer 80 cm across.
  • Make players turn. Spread targets all round them, behind too, and always add edge arrows with v.pointers() so they can find them.
  • Use the helpers. v.forward(), v.heading() and v.offAim(p) tell you where the phone points; v.toScreen(x, y, z) gives screen positions for taps and labels.
  • Keep it phone-friendly. AR shares the one 3D renderer with the console games, so keep meshes few and simple.

Fallbacks are required

Every AR game must play everywhere. With no camera (refused, or on a computer) the kit draws a virtual room instead. With no motion sensor, the player drags to look around (v.drag(dx, dy)); if dragging is already your control, keep targets in view instead. Stop the camera with v.off() in reset() and before api.over(). The camera picture is never saved or sent.

Test the fallback path with the usual checks (smoke, fold, sweep), then try it on a real phone, because the camera and motion sensor only work there. The full reference, including how to fake a camera in a headless browser, is in docs/ar-3d.md.

4. The engine: everything on gs

Everything the app offers games comes through one import, import gs from '../gamescroll.js'. A game can't import any other app code. Use these rather than writing your own: games come out shorter and feel better. Every part has a short guide (what it is, what to know, its types and the real games that use it), and npm run kit physics prints one.

  • Feel and sound. gs.effects (feel.coin(), feel.hit(), feel.boom(): particles, shake, sound and haptics in one call), gs.juice, and gs.sound: 98 ready-made sounds, music and tunes made in code, world sounds and voices, and a soundtrack that follows the action with one line (music: 'chase').
  • Controls. gs.controls (thumbsticks, buttons, taps, holds, swipes), gs.pad (game controllers), gs.moves (swing, punch, throw or flip the phone), gs.aim (aim assist for thumbs), gs.strokes (shapes the player draws), gs.drag and gs.ui (menus in your own look).
  • Rounds and pacing. gs.rounds (Ready, scenes, levels), gs.pacing (spawners, waves, a director that eases off), gs.things, gs.tick, gs.math (seeded random, daily seeds, timers that pause with the game), gs.history (undo) and gs.replay (ghosts).
  • 2D worlds. gs.physics (Rapier: shapes that tumble, joints, ropes, ragdolls, grabbing), gs.soft (cloth, rope, jelly, liquid), gs.sand, gs.flow (rivers and floods), gs.tiles, gs.movers (jumps that feel right), gs.camera2d, gs.look2d (2D lights and shadows that glow, screen effects), gs.pixel, gs.gfx, gs.sketch, gs.bones, gs.anim, gs.art, gs.icons (528 icons, never emoji) and gs.fonts.
  • Opponents that think. gs.brains, our Tiny Brains: opponents and helpers that learn on the phone as people play, with guard rails so they stay fun, corrections you can give them ("here the right move was this"), a memory of which moves made rounds exciting, and a dial that keeps a player winning about as often as you choose. gs.battle, gs.fight and gs.vehicles come with ready-made opponents; gs.ai, gs.senses, gs.stealth and gs.solve give chasers, guards that see and hear, and puzzles with one answer.
  • Kinds of game. gs.board (match, fall, slide, flood), gs.cards, gs.dice, gs.words, gs.trivia (about 2,700 questions), gs.rhythm, gs.idle, gs.party (pass the phone, split screen), gs.sports, gs.arena, gs.bullets, gs.adventure, gs.hex, gs.rts, gs.gen (dungeons, caves and mazes from a seed), gs.items and gs.stats.
  • Stories and fantasy. gs.rpg (levels, skill trees, reputation, quests and a journal), gs.story (branching talk, played by people in 3D), gs.town (a living town with a clock), gs.dungeon, gs.magic, gs.monsters (telegraphed attacks, bosses in phases), gs.companions, gs.mounts (horses and flying beasts) and gs.campaign.
  • Action. gs.combat (guns, bows, explosives, health), gs.fight (motion inputs, 3D melee with swords and shields), gs.tactics (cover in 2D and 3D, squads), gs.climb (ledges, ropes, swimming), gs.gadgets, gs.missions (objectives, open-world jobs, phone calls), gs.cutscene and gs.prompts.
  • 3D worlds. gs.toon, gs.hd, gs.ar and gs.tabletop for the 3D styles, with gs.camera, gs.physics3d, gs.fx3d, gs.sky (time of day and weather), gs.outdoors (land, grass, sea, rivers, trees, cloth), gs.city (a big streamed city with rooms behind the doors, traffic, police and a GPS), gs.vehicles (cars to drive, get into and crash), gs.craft, gs.models (people, creatures and a character creator, made in code), gs.poses, gs.characters, gs.nav3d, gs.props, gs.regions, gs.voxels, gs.fluid (liquid, sand, snow and mud), gs.gas (smoke and fire), gs.destruction, gs.level3d and gs.bricks.
  • The real world. gs.device (haptics, tilt, shake, compass, mic, camera), gs.vision (face, hands and body, all on the phone), gs.hear (sounds and spoken words), gs.doodle (guesses what a player drew), gs.geo, gs.real (the sun, the moon, the battery) and gs.phoneai (the phone's own AI, for flavour lines only).

The kits find each other: one Wind blows the grass, trees, rain and smoke, and a 3D world is found by the cars, guns and cloth in it, so you don't wire them together. Kits give answers (hits, timings, where to aim); how your game looks and what scores stays yours. The maker kit is the long reference with examples.

Sensors return nothing in the browser or when a player says no, so every sensor game needs a touch fallback: drag instead of tilt, tap instead of blow. Stop the mic or camera when the round ends. Location, camera and mic data must never leave the phone.

Location games

A game can build its level from the player's area (a daily puzzle shared with everyone nearby, local weather, monsters that live in this park) or be played by walking around. Say how precise it needs to be in the game definition:

export default { id: 'park-hunt', /* ... */ location: 'coarse', make };   // or 'precise' for walk-around games

// inside make(api), during play (for example in update, the first time it runs):
api.location().then(here => {
  // { lat: 51.51, lon: -0.13, accuracy: 1100, real: true, precision: 'coarse' }
  // or the stand-in { lat: 0, lon: 0, real: false, reason: 'denied' | 'off' | 'unavailable' | 'not-playing' }
  buildLevel(here.real ? cellId(here, 2000) : dailySeed);   // cellId from gs.geo
});
  • Rounded for you. 'coarse' (use this unless you truly need more) rounds to about 1 km. 'precise' rounds to about 10 m, for games played by walking, and a maintainer checks it's needed.
  • Only during a round. The phone asks the first time a player presses Play on a location game, never before. Before Play and after the round you get the stand-in. The feed tells players "Uses your rough area" on the start screen.
  • Always playable. When the player says no, switches it off in Settings, or is indoors with no fix, you get real: false. Fall back to a daily seed, or let the player walk the stand-in around by touch with offset(here, east, north).
  • api.watchLocation(cb) calls cb straight away and each time the rounded spot changes. It stops by itself when the round ends; it also returns a stop().
  • Never read navigator.geolocation yourself, and location never leaves the phone. There are no map tiles yet, so draw the area yourself.
  • Older versions of the app don't have this, so they skip location games until they update.

5. Credits and shop items

Winning any game pays credits, which is why goal is required. Pick a goal a decent player reaches in about a minute. You can also sell items for credits:

reward: 10,   // credits per win; the first win pays double
shop: [
  { id: 'shield', name: 'Shield', price: 25, kind: 'boost', desc: 'Survive one crash.' },
  { id: 'gold', name: 'Gold Skin', price: 150, kind: 'unlock', desc: 'Forever gold.' },
],
// in your game: if (api.has('shield')) { ... }

6. Test it

Play it on a real phone if you can: check the controls feel good with a thumb, the hint makes sense, and the goal is reachable. Then run the same checks the pull request runs, all in one command:

npm i --no-save playwright && npx playwright install chromium   # first time only
npm run check tap-bubbles             # every check, one report: each problem with its line and what to do
npm run check tap-bubbles -- --quick  # just the code checks, in about 2 seconds

It checks your code uses only gs, and uses it the way its types describe; names the three games nearest to yours (a near-copy fails); builds it; plays it with random taps, streamed the way the app runs it, and while folding the screen; plays 3D games long at odd screen sizes; has a bot try to reach the goal; and ends with the speed report: frame time against the budget on a slowed processor, your slowest lines, garbage and memory, and for 3D games draw calls, triangles and shaders built mid-play against low, mid and top phones. Making your game run well on phones is your job, so fix its warnings too. A frame lab recording from a phone gets the same advice: npm run speed -- --lab <file>.

To see how a real game uses a part of the engine, run npm run examples Feel.coin (or Physics.rope, rope...): the shortest games that use it, with the lines.

7. Submit it

  1. Commit your game file on a branch of your fork and push it.
  2. On GitHub, open a pull request against main of robthewizzuk/game-scroll.
  3. Fill in the template: what the game is, why its mechanic is new, its style, and a screenshot or short clip.
  4. The automatic checks run npm run check on your game, speed report included. Fix anything they flag. A "plays like" warning names the nearest game: say what makes yours play differently, or change it until it does.
  5. Rob plays it and may ask for changes. Games that break the rules or play too much like one already in the feed may be turned down.

A game pull request should only add or change your file in src/games/. Changes to shared code ship inside the app and need an app update, so open those separately and explain why.

After it's merged

You don't need to do anything. Every merge builds each game as its own small file and uploads it with a new catalogue. Phones check the catalogue regularly, so your game appears in feeds within minutes, credited to you by your GitHub name. Fixes reach players the same way.

The feed is play-tested as a whole, and games that turn out weak or broken may be hidden or removed later, so the 1,000 stay worth playing.
